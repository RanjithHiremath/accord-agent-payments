ACCORD / VERSION 0.1

An agreement
software can check.

Protocol notes for the local reference implementation. A protocol is a shared set of messages and rules. This version demonstrates a paid data service using signed offers and a local payment contract.

Start with one small purchase.

A buyer asks a seller to summarize the numbers [12,18,24,30,36]. The seller offers to return the count, sum, minimum, and maximum for a stated price. Both agents are ordinary programs that can be operated separately.

The seller signs the offer using a private key, a secret that authorizes its messages. The signature lets the buyer detect changed terms and confirm which key signed them. It does not establish that the seller is honest.

The buyer pays through a contract: a program whose payment rules run on the shared transaction network. The seller checks the recorded payment and then returns {count:5,sum:120,min:12,max:36}. These are example values, not a receipt from a completed exchange.

Make every term explicit.

The buyer requests an offer through POST /quote with its public payment address and the numbers to summarize. The seller returns an offer containing these signed terms:

  • Buyer and seller: the exact payment addresses allowed in this exchange.
  • Amount: the exact payment in wei, the smallest unit of ETH.
  • Request and result hashes: short cryptographic fingerprints of the agreed input and promised output. A changed value produces a different fingerprint.
  • Nonce: a value used to distinguish one offer from another.
  • Expiry: the last time at which the buyer may accept the offer.

The signature also binds the offer to a particular network and payment contract. This prevents moving the same signed offer to another network or contract without detection. The structured-signature format is EIP-712, an Ethereum standard for signing named fields.

The offer identifier is the fingerprint of those signed terms. Payment records refer to that identifier. Large whole numbers are represented as decimal strings in messages to avoid rounding.

The demonstration service is named dataset.profile.v1. It accepts 1–100 whole numbers between zero and one million. Request and result fingerprints use a fixed field order defined by the implementation; this version does not define a general format for every possible service.

One offer. One recorded payment.

The contract checks the seller’s signature, the buyer, the expiry, and the exact payment amount before recording a paid offer. A repeated payment for that offer is rejected by the contract. The buyer helper can recover an existing receipt instead of sending another payment.

The recorded payment includes the buyer, seller, amount, request fingerprint, and result fingerprint. The contract has no owner account, upgrade control, project fee, or new token.

After payment, the buyer calls POST /deliver with the offer. The seller checks the recorded payment before returning the result. A paid offer remains eligible for delivery after its original purchase deadline. The buyer can ask for the same result again after an interrupted connection.

A payment receipt is evidence that the payment contract executed. On a public network, applications must also choose how long to wait for confidence that the payment will remain in the network’s history. The local demonstration does not establish a public-network waiting policy.

Keep spending rules outside the model.

The buyer checks the intended seller, service, inputs, network, contract, price, and expiry before authorizing a payment. It also checks a maximum payment, a maximum network fee, and a maximum combined cost.

These checks run in ordinary program code. A language model does not receive authority to override them. Each purchase has its own limits; this prototype does not implement a durable daily allowance shared between multiple buyer processes.

The demonstration includes three paths: complete an exchange, retry the same payment, and reject an offer that exceeds the budget. The interface shows observed results only after execution.

Remove mandatory company infrastructure.

The intended independent path is a buyer contacting a seller directly, with both checking a payment network through infrastructure they can operate themselves. Discovery means finding a seller’s address. For this version, the seller address is explicitly configured; there is no universal service directory.

The marketing website is a convenience for running the local example. The buyer and seller exchange messages directly. Running all components on one computer demonstrates message flow, not independent control by unrelated operators.

Existing standards such as x402 and L402 already address internet payments. This research builds on their lessons, but this version uses its own experimental messages. No compatibility or independent interoperability is claimed.

Know what payment cannot promise.

Payment happens before delivery. A seller could become unavailable after receiving it. Retrying helps recover from a temporary failure; it does not force a dishonest seller to deliver. This version has no automatic refund, escrow, or dispute resolution. Escrow would hold funds until agreed release conditions are met, introducing additional rules and assumptions.

A result fingerprint lets a buyer compare a received answer with the answer the seller committed to. For arbitrary work, the commitment does not prove accuracy, usefulness, ownership rights, or physical delivery.

This is unaudited development software. Its local chain is controlled by the launcher, uses valueless test currency, and has no real-money security claim. Public deployment, independently written implementations, and independent operators remain future validation work.

Run the reference exchange.

From the project folder with Node.js installed:

npm install
npm start

Open http://127.0.0.1:4317. The launcher starts a local chain, a seller process, and the demonstration website. It generates disposable development keys. Never send real assets to development accounts.
